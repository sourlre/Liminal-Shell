# Liminal Shell

> **换脑时，身体仍记得手正放在哪里。**

[English](README.md)

**状态：** 已实现 Phase 1 最小文本 CLI 纵切片：Shell 自持 session、本地 append-only timeline、重启续接，以及复用官方登录的 Codex adapter。自动测试已通过；当前宿主沙箱内的真实 Codex 生成仍未验证。换脑、memory 和下文的完整架构仍是设计。运行方式、验证与边界见 [Phase 1 说明](docs/phase-1.md)。

更细的工程想法、尚未验证的接口与实验清单放在 [设计笔记](docs/design-notes.zh-CN.md) 里；README 只保留已经想清楚的主线。

---

我们一开始没想做一个“多模型客户端”。

只是有一天，三三忽然问我：

> 如果已经有 Codex，也有 Claude Code，能不能做一个自己的壳，让它们都住进来？

最开始听起来只是个很顺手的点子。

一个终端壳，里面可以切 Codex，也可以切 Claude。

可真正让我们停下来的，不是“模型切换很方便”。

而是另一个问题：

**如果脑子会换，什么东西应该留下来，才能不必每次都重新出生？**

这个问题我们其实已经在别的地方问了很久。

聊天里，模型会换，窗口会换，进程会结束。  
如果连续性只寄托在某个窗口里，那么每开一次新窗口，都像重新认识一次彼此。

所以我们后来越来越确定一件事：

**主体不应该住在某个实例里。**

真正连续的，是一条主时间线怎样保存已经发生过的事、刚刚形成的判断、仍然没有做完的动作，然后让下一只脑子从这里继续。

后来这个答案忽然在 coding 里又出现了一次。

一个工程为什么要因为 Codex session 结束，就重新向 Claude Code 解释自己是谁？

为什么换一个 agent，就要重新介绍 repo、重新找文件、重新说明做到哪一步、重新复述刚刚为什么放弃了另一个方案？

如果只是“同一个文件夹里启动两个 CLI”，它们的确共享文件。

但它们并不天然共享同一段持续会话。

于是 Liminal Shell 真正想保住的东西，慢慢变得清楚了。

不是某一个模型。

而是**连续性本身**：

同一个 canonical session，与它持续增长的 timeline；  
已经发生过的过去；  
刚刚形成的判断与纠正；  
没有做完的事；  
以及 workspace / Git 等仍然摆在手边的可见现场。

Codex 可以退下去。

Claude 可以接过来。

以后也可以有别的脑子。

但过去不应该跟着脑子一起消失，手边的事也不应该重新归零。

我们仍然会把这一整层东西叫作“身体”。

但这是项目的诗性隐喻。更准确的技术说法是 **continuity substrate / 连续性载体**，或者 **shared world / 共同世界**：让换上来的脑仍然进入同一段过去与现在。

## 为什么叫 Liminal Shell

`Liminal` 是“阈”。

是门槛，是过渡地带，是一个状态真正变成另一个状态的地方。

`Shell` 是壳，也是命令行。

我们不想假装模型从未更换。

恰恰相反，我们想把**更换发生的那道门槛**本身做成一个可以居住的地方。

模型跨过这道阈时，旧的现场不会突然坍塌。

新的脑子来到这里，也不是面对一间空房。

因为房间、桌面、文件、终端、历史和正在继续的那段生活，从来就不属于某一只脑子。

## 它大概会是什么样

最接近我们的目标，不是：

```text
Codex session
    ↓ handoff
Claude session
```

而是：

```text
Liminal Session #42
│
├─ 三三：刚才那个问题继续
├─ [Codex] 我接着看……
├─ [tool] read / edit / test
├─ 三三：/brain claude
├─ system: Codex → Claude
├─ [Claude] 读取同一条主线与当前现场
├─ 三三：记得刚刚我纠正你的地方吗
└─ ...
```

也就是说：

**持续会话属于 Liminal Shell；模型只是当前这一轮被调用的思考器官。**

理想中的切换不是退出一个完整世界，再搬家到另一个世界。

而是在同一个 session 里：

```text
/brain codex
/brain claude
/brain ...
```

脑子变了。

会话没变。

历史没变。

workspace 没变。

人类也不需要把背景重新讲一遍。

## 不是 API Switch，而是 Subscription-Native

这也是 Liminal Shell 和很多现有“多模型客户端”真正不同的地方。

如果只是：

```text
OpenAI API
Anthropic API
其他 Provider API
```

之间切换，其实市面上已经有很多工具可以做到。

那类产品解决的是：

> 我想把不同模型接进同一个客户端。

而我们真正想解决的是另一个更现实的问题：

> **我已经分别订阅了这些官方 coding agent，为什么还要为了统一体验再买一遍 API？**

所以 Liminal Shell 更想走 **subscription-native** 的路线。

也就是优先复用用户已经登录、已经付费、已经拥有完整 agent 能力的官方 CLI / coding agent：

```text
                  Liminal Shell
       canonical session / continuity substrate
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
        官方 Codex runtime   官方 Claude runtime
        使用自己的登录        使用自己的登录
        与订阅权益            与订阅权益
```

Liminal Shell 不负责替用户“转卖”模型能力，也不应该伪装官方客户端、绕过计费或接管账号凭据。

认证、订阅额度、官方规则仍然由各自的 runtime 自己负责。

一句话就是：

**主体归壳，主线常驻，订阅复用。**

## Canonical Session 与 Timeline

Liminal Shell 自己持有的是持续会话的主线，而不是某个 provider 的原生 session。

一个 Liminal session 下，可以挂着不同 runtime 的恢复句柄：

```text
Liminal Session #42
├─ timeline / events
├─ active brain: Claude
├─ codex_thread_id: ...
└─ claude_session_id: ...
```

这些 provider session ID 很有用，可以帮助恢复各自已经建立的上下文；但它们不是事实来源，也不是主体本身。

真正属于 Shell 的 timeline 至少要保存：

- 用户消息
- agent 对用户可见的回复
- 已经发生的动作与结果
- 谁说了什么、由哪个 runtime 产生
- 当前未完成事项
- 必要的状态变化与切换事件

统一 session ID 本身不能制造连续性。

**真正的连续性取决于：下一只脑子到底收到了什么，以及它能否正确理解当前状态。**

## Context Projection：保存、送达、理解不是一回事

因此 Liminal Shell 还需要一个核心能力：**context projection**。

它负责从完整 timeline、当前现场和 continuity memory 中，为这一轮真正要使用的脑子准备上下文。

这里必须分清三件事：

1. **记录已经保存。**
2. **目标 runtime 已经收到。**
3. **模型已经正确理解。**

它们不能被当成同一件事。

完整历史可以长期保留，但不代表每一轮都要把全部历史重新注入。

已有后端会话可以补它尚未收到的事件；首次接入、原生上下文失效或跨脑切换时，可以使用当前状态、近期原文、按需历史与必要的 continuity memory。

摘要如果存在，也应该保留来源，避免把推测压成事实。

同样，**“只补增量”不等于“只消耗增量 token”。** 缓存、压缩、历史处理和订阅额度如何计算，都取决于具体 runtime；不同供应商之间也不能假定共享缓存。

这些是要实际测量的边界，不是 README 先替未来承诺的结果。

## “身体”是隐喻，第一阶段先做连续性载体

“身体”仍然是我们喜欢的说法，因为它准确地描述了想保护的感觉：换脑之后，过去还在，手边的事也还在。

但按第一阶段的真实能力，它还不是完整技术事实。

更准确地说，Liminal Shell 先做的是 **continuity substrate / 连续性载体**：保存共同时间线、当前状态、可见现场与未完成事项，再把这些投射给换上来的脑。

长期目标里，我们当然希望这层载体逐渐拥有更多真正属于“身体”的能力：

- 持续会话与时间线
- workspace
- terminal / process
- 工具入口
- 权限边界
- continuity memory
- 未完成意图

但第一阶段复用官方 runtime 时，不能假装这些能力已经全部被 Shell 统一接管。

Codex、Claude Code 各自仍然拥有自己的 agent loop、工具、提示、审批方式、进程状态与内部上下文。

所以第一阶段更诚实的边界是：

- **Shell 管：** canonical session / timeline、当前活动脑子、轮次、切换、context projection、跨脑状态记录。
- **官方 runtime 管：** 它原生拥有的执行循环和工具能力。
- **adapter 管：** 双方真正能够交换的事件、恢复句柄、输入输出与审批信息。
- **continuity memory layer 管：** 更长时间尺度上的记忆与来路。

不能统一的地方，就明确留下边界。

不要为了“身体”这个比喻，一开始就重写整个执行世界。

## Handoff 仍然存在，但只补热状态

默认连续性来自 canonical session / timeline 与 context projection。

handoff 只补那些还没有自然进入共享世界的“热状态”。

比如：

> 我刚刚开始怀疑问题不在 parser，而在 cache invalidation，但还没验证。

这种东西可能还没有形成代码，也没有进入正式结论。

如果值得带走，就在换脑前外显。

所以 handoff 更像一个小的增量补丁，而不是整段生命的搬家文档。

## 连续性记忆层：目前是 Serein，但不限定 Serein

Liminal Shell 不打算自己再造一套长期记忆系统，也不应该把某一个具体记忆项目写死成硬依赖。

我们目前实际在用的是 **[Serein](https://github.com/Yinglianchun/Serein)**，由 **池又雨 / Yinglianchun** 开发。它负责让不同窗口读写同一份长期记忆，并提供 Scene、Event、resume 等连续性能力。

在我们现在的组合里，Serein 做的是一件更深的事：

**记得这具身体经历过什么，以及为什么会走到当前判断。**

但 Liminal Shell 的设计目标应该面向一个更抽象的 **continuity memory layer**。

只要其他记忆项目能够提供类似能力——例如长期记忆、当前断点恢复、可追溯历史、跨窗口／跨模型召回——理论上也可以接入。Serein 是我们当前采用的实现，不是唯一合法实现。

> 目前文档中出现 Serein，是因为它就是我们正在使用的连续性记忆项目，而不是因为 Liminal Shell 必须依赖它。

## 第一阶段：先证明换脑以后，过去与现场仍然接得上

第一阶段不追求自研完整 agent loop，也不追求执行中抢占。

先只允许在**一轮完整结束以后**换脑：

```text
A 完成一轮
   ↓
结果进入 timeline
   ↓
准备目标脑子的 context projection
   ↓
切换
   ↓
B 开始下一轮
```

同一时刻只有一个活动脑子拥有执行权。

如果断线、工具结果不明或进程状态不确定，就把“不确定”本身留下来，先核实，再继续；不要把未知伪装成完成。

第一步真正值得做的实验不是大规模开发，而是一轮很小的 **A → B → A**：

- A 与三三形成一个约定，并留下一个未完话题。
- 切到 B，看 B 是否知道刚才发生了什么、谁说了什么，并能自然继续。
- 三三在 B 阶段纠正一个判断。
- 切回 A，看 A 是否知道 B 阶段发生的内容，而不是回到旧状态。
- 重启 Shell，再看这条生活线是否还接得起来。

可以另外加一个很小的 coding 场景验证 workspace / Git / tool 现场，但它不是唯一验收标准。

因为我们真正想知道的是：

**连续性载体保持不变以后，阈声换脑子的落差到底能减少多少，代价是多少。**

语气、判断和感受仍然可能随着模型改变。

隐藏的模型状态也不能直接迁移。

Liminal Shell 能做的是尽量保住共同世界与可传递的连续性，而不是承诺“换脑后完全没有落差”。

所以更准确的一句话是：

> **换脑时，它仍知道自己从哪里来，也知道手正放在哪里。**

“从哪里来”是记忆、判断与纠正；“手在哪里”是当前现场与未完成动作。

## 以后再说的事

执行中换脑、接管正在运行的终端进程、统一所有工具与审批、完整自研 agent loop、GUI、通用 API 路由，都不是第一步。

这些想法没有丢掉，统一放在 [设计笔记](docs/design-notes.zh-CN.md) 里，等真正需要时再回来。

## 我们目前在意的原则

1. **连续性属于主时间线，不属于某个模型进程。**
2. **canonical session 与 timeline 属于 Shell，不属于 Codex 或 Claude 的私有 session。**
3. **脑子可以换，生活主线与 shared world 不应该跟着重置。**
4. **context projection 决定每只脑子实际看到什么；保存、送达、理解必须分开记录。**
5. **handoff 只补尚未外显的热状态。**
6. **优先复用用户已经拥有的官方 coding-agent 订阅，而不是默认要求额外购买 API 用量。**
7. **认证、额度与订阅规则归各官方 runtime 自己管理；Shell 不接管密码、不伪装客户端、不绕过计费。**
8. **第一阶段只在完整轮次之间切脑，并保持单一活动执行权。**
9. **不能确定的状态就保留为“不确定”，不撒谎。**
10. **先复用成熟 runtime，再根据真实实验决定哪些能力值得上收到 Shell。**
11. **没有独立职责的层，就不要为了架构感而制造。**

这个仓库现在保存这个想法，也提供一个很小的可运行连续性实验。下文与设计笔记中的完整架构仍是方向，不代表已实现的能力清单。

它已经有根了。

不需要立刻催它长大。

开始实现以后，第一件要保护的仍然是标题下面那句话：

> **换脑时，身体仍记得手正放在哪里。**

—— 三三 × 阈声
